# 單機 → 內網多人 升級路徑 v0.1

> 延續自 [2026-07-19 brief 與深化分析](2026-07-19-brief與深化分析-v0.1.md)。本文件回答一個問題：**目前工具只能單機單人使用，要變成「別人能真的接派工／確認」需要做什麼、怎麼排、UI 怎麼優化。** 標註「🤖 AI 補充」處為分析觀點，非討論結論。

---

## 0. 一句話結論

現況是**單機、單一設定身分**，「多人互動」是靠一個人切換身分演出來的。但好消息是——**架構本來就是主從式（browser ↔ python server）、狀態集中在 server 的 JSON、前端每 8 秒輪詢**，這三件事就是多人協作的骨架。所以升級不是重寫，是「打開幾道開關 + 補幾個洞」。

---

## 1. 現況的真相（離多人有多遠）

三個讓它「目前只能單機單人」的具體點，都在現有程式碼裡：

| # | 現況 | 位置 |
|---|---|---|
| 1 | 伺服器綁 `127.0.0.1`，只有本機連得到 | `server.py`（`ThreadingHTTPServer(("127.0.0.1", port), …)`） |
| 2 | 身分是單一值 `currentUser`，前端所有「我是誰」判斷（`me()`）與動作的 `actor` 都用它 | `config.json` / `app.js` |
| 3 | 「已通知全員」是前端 toast 字串，後端沒有真的寄任何東西 | `app.js`（confirm 後的 toast） |

補充：多專案切換（`currentProject` / `projects` / `data/<專案id>/`）已支援，但那是「一台機器管多個案子」，**不等於多人**。

所以現況＝**一台電腦、一個操作者**，用切換身分把多人劇本演一遍，驗證狀態機與 UI 邏輯。這在 dogfooding / demo 階段合理。

---

## 2. 一條鐵則（決定架構怎麼長）

> **CAD 的「複製到本地 + 開檔」，程式一定要跑在「使用者自己的電腦」上。**

原因：`shutil.copy`（複製）與 `os.startfile` / `xdg-open`（開檔）都寫在 `server.py`，**在跑 server 的那台機器上執行**。單機時 server = 使用者電腦，沒問題；一旦變成「一台中央 server、大家用瀏覽器連進來」，複製會落在**中央 server 的硬碟**、CAD 會開在**中央 server 的螢幕**，使用者的電腦只是個顯示器。

而**瀏覽器是沙盒**：一個從遠端 server 送來的網頁，基於安全限制，不能把檔案寫進你的硬碟、也不能啟動你的 AutoCAD。這是瀏覽器鐵律，不是程式寫得好不好。

所以「clone 到本地再開」的 git 模型，卡在 client-server 邊界上——在中央 server 模型裡，「git 指令」（複製邏輯）在 server 上跑，不在你的機器上跑，「本地」＝ server。

> 現況補充：目前 accept 其實**還沒真的複製**，只是設 `localCopy=True` + log 一行「建立本地副本」，實際直接開中央檔。所以 clone-push 是**尚未實作、現在從零設計**的部分——正好一次決定對。

---

## 3. 兩個部署模型（鐵則收斂出的選項）

| | **模型 B：人人自跑 agent**（建議） | 模型 A+：中央 server + 本機小助手 |
|---|---|---|
| 做法 | 每人跑 `server.py`，全部指向**共用網路磁碟**當中央檔 | 中央 server 管狀態/UI/PDF；每人電腦另跑一個超小「開檔助手」，瀏覽器喊 `localhost:助手埠`「在我這台開這檔」 |
| CAD 複製/開檔 | ✓ 在自己機器，正常 | ✓ 由本機助手做，正常 |
| 狀態併發 | 多 server 寫共用 JSON，要處理檔鎖（較麻煩） | 只有一個中央 server 寫，乾淨 |
| 部署 | 每人裝 Python、跑腳本 | 中央一台 + 每人裝小助手 |
| 複雜度 | 低（幾乎就是現況指向共用磁碟） | 中（要多寫本機助手） |

**建議走模型 B。** 幾乎不改架構——「大家各跑一份、指向共用磁碟」，原本的 clone-push 直覺原封不動成立。代價只有共用 JSON 併發，而團隊人少、且 lock 模型本來就擋「同一份圖同時被兩人動」，pilot 階段用 `threading.Lock` + 樂觀鎖擋掉明顯 race 即可。等長大再考慮模型 A+。

> 為什麼你的「複製到本地再開」在模型 B 成立：因為每一步程式都在使用者自己機器上跑，「本地」就真的是自己的電腦——從共用磁碟複製一份到本機 → 開本機檔改 → 確認後推回共用磁碟取代。

## 4. 分階段升級路徑

原則：每階段能獨立產生價值、判準明確。**建議 S1 → S2 → S3 → S4，S1 之後可先停下 dogfooding。**

| 階段 | 目標 | 改動量 | 判準（做到才算過） |
|---|---|---|---|
| **S1 內網互通 + 多身分** | 別人連得到、能扮演自己接派工 | 小 | 兩台電腦兩個人：A 派工 → B 在自己電腦接 → A 確認，全程零口頭 |
| **S2 真實登入 + 追責** | 身分不可造假 | 中 | 每個動作 actor = 登入者，改錯查得到是誰 |
| **S3 真實通知** | 派工/退回/進版對方真的收到 | 中 | B 不用一直開著網頁也知道有新任務 |
| **S4 跨人鎖定** | 檔案 check-out 真正互斥 | 中 | A 鎖住的圖，B 那邊按鈕反灰，看得到誰鎖、鎖多久 |

### 各階段解析

**S1（內網互通 + 多身分）** — 三個洞：
1. **綁定位址**：`127.0.0.1` → `0.0.0.0`，別人用 `http://<區網IP>:8734` 連。一行。
2. **身分不再寫死**：前端頂部「目前身分」下拉，選了存 localStorage，每台電腦記自己是誰。**先不做密碼**（信任制）。
3. **併發安全**：`ThreadingHTTPServer` 多執行緒，兩人同時動同一份 JSON 會 race。加 `threading.Lock` 包住 load-modify-save。**不做會掉資料，必做。**
4. **CAD 開檔**：走模型 B，開檔在各自機器正常。（若暫時仍是中央 server，降級成「複製檔案路徑」按鈕，使用者自己從檔案總管開。）

**S2（登入）**：輕量登入（帳號密碼，或「選名字 + 團隊共用密碼」）+ session cookie。真正意義不是技術，是 brief 2.5 的**追責政治**——身分不能造假，「有紀錄 = 改錯不是你的錯」才站得住。

**S3（通知）**：roadmap 的 email 接入 / LINE bot。派工、退回、進版時觸發。

**S4（跨人鎖定）**：現在 `localCopy` 只是 flag，沒按「人」互斥。多人後 enforce：只有接受任務者能 submit，別人看到鎖定。brief 2.2 的 lock 模型真正落地。

## 5. S1 實際操作步驟（模型 B，做完後怎麼用）

1. **改程式**：bind 改 `0.0.0.0`；前端加身分下拉；加併發鎖。（工程項）
2. **每人跑一份**：team 成員各自 `python server.py`，或指定同一台當共用入口。
3. **資料指向共用磁碟**：`config.json` 的專案資料夾（CAD / PDF / 信件 / 筆記）與 `data/` 指到大家都連得到的網路磁碟（`\\NAS\案件\928816\…`），狀態才是同一份。
4. **選身分**：各自在右上角「目前身分」選自己的名字（選一次，記住）。
5. **走一次真實流程驗證**：阿勳從收件匣建 request 指派給小柯 → 小柯 8 秒內「🔧 待辦作業」跳數字、接受、開本機 CAD 改、提交 pending → 阿勳「👁 待我確認」跳出、檢視 PDF、確認進版 or 退回重修 → 兩邊歷程同步。**全程無口頭交代**＝判準過。

## 6. UI 易用性優化（多人化才浮現的問題）

單機不痛、一多人就痛的點，按投報率排：

1. **身分要「一直看得到」且切換零摩擦** 🔴最重要
   頂部常駐「👤 目前身分：小柯 ▾」。信任制下最大災難是「我以為我是阿勳結果用小柯身分進版」。第一次強制選、記 localStorage，動作按鈕旁隱約提示「以 小柯 身分」。

2. **新任務要「有感」，不能只是靜默輪詢**
   8 秒輪詢是無聲更新。被派工要「知道」：待辦數字增加時 badge 跳動 + toast「🔔 阿勳 指派了新任務給你」。不用真推播，輪詢 + 視覺提示對 S1 夠用。

3. **鎖定狀態顯示「誰 + 多久」**
   現在有 🔒 pill 但沒說是誰。改「🔒 阿勳 編輯中・已 2 小時」。直接解 brief 2.2 的痛（檔案被誰開著沒人知道）——不是繞過，是可視化。

4. **不可逆動作帶身分二次確認**
   「確認進版」「退回重修」影響別人，跳小確認框：「你將以 **陳監造** 身分確認 REQ-042 進版，通知全員舊版作廢」。防手滑、強化追責感。

5. **CAD 開檔降級要優雅**
   別留一顆會「在別人電腦開檔」的按鈕。偵測 localhost（server=client）則保留自動開；否則換「📋 複製檔案路徑」+「請從檔案總管開啟」。

6. **給審核者手機/平板檢視** 🟡高價值但較大
   監造、業主常在工地拿平板。現在三欄式純桌面。若 requester 能在手機「看 pending PDF → 確認/退回」，採用率大幅拉高——正中「低摩擦、無痕融入」定位。較大，可放 S3 前後。

## 7. S2 隱私與權限模型（2026-08 釐清）

儀表板要讀全專案任務、信件從私人信箱進到共享任務、同一任務會不會被重複接受——
這三題都繞著**同一條軸：信件從「私人信箱」跨進「全平台可讀的共享任務」的界線**。
且三者要**真正強制執行（不是靠自律）都得等 S2 登入層**：沒有登入就沒有伺服器級的
「誰能讀什麼」管制——現況所有任務都送到每個瀏覽器、前端只是 client-side 過濾，等於沒有隱私。
以下是「登入之後長怎樣」的規格。

### 7.1 私有／共享界線：Request 建立的那一刻

```
信件進私人信箱（私有）
  → AI 在你的私有情境裡分類、建議（仍私有，只是你的待審佇列）
  → 建立 Request  ←── 這一刻跨界，變成共享任務
  → 上專案看板，可派工、可追蹤
```

兩個必守原則：
1. **只有「結構化投影」跨界，不是整封信**——跨過去的是 {圖號、要求、requester、期限、一小段引文}，
   不是原始信件全文、更不是信箱裡其他無關內容。`source.quote` 要是最小必要摘錄。
2. **參考資料與雜訊永不跨界**——留在私人信箱，或（人主動決定時）才歸進專案參考池。

自動建立也守這條線：高信心自動建任務時，(a) 只送投影、(b) 標記「AI 自動建立・待稽核」，
**原始信件仍留在私人信箱**。AI 是在你的信箱裡「幫你讀」，不是把信箱攤開給全公司。

### 7.2 隱私分層：誰看得到什麼

| 資料層 | 誰該看得到 | 理由 |
|---|---|---|
| 任務的存在／狀態／派給誰 | 全專案成員 | 協作座標，不是隱私（要知道哪張圖誰在改才不撞車） |
| 每人負載彙總（手上幾筆、誰過載） | 限主管／PM | 用來調度人力，不該變成同儕互看 |
| 效率／速度排名（誰快誰慢） | **預設不做** | 監控陷阱，踩 brief 2.5 政治；導入話術是「保護執行者」，一旦變排行榜就被抵制 |

結論：**任務狀態全專案透明、人力負載只給主管、不做速度排行**。儀表板定位是「調度與防漏接」，不是考核。
私人信箱永遠不共享。

> 註：儀表板**畫面**可在 S1 就先做（純看現有任務資料、trust-based 先讓大家都看得到、無 AI），
> 立即有價值；但上述**隱私分層的強制執行**要等 S2 登入。

### 7.3 重複接受與互斥（三個層次）

1. **任務層——派給誰**：採**預先指派制**（建 Request 時就有 designer，AI 建議＋人可改），
   只有該 designer 的「待辦」看得到 → 本質上不會重複接受。換手是明確的「改派」動作，不是第二次 accept。
2. **圖檔層——真正的衝突點**：兩個不同任務動到同一張 DWG，二進位檔不能 merge（brief 2.2），
   兩人同改必有一人白工。所以 **accept = 對「那張圖」上鎖（check-out）**，同張圖的第二個任務只能等解鎖。
   這也順便可視化「誰鎖了哪張圖、鎖多久」（＝ UI 優化 #3）。
3. **併發層——競態防護**：現在 `transition()` 有檢查 `status==red` 才 accept，但 `ThreadingHTTPServer`
   多執行緒下兩個 accept 可能同時通過檢查（讀→改→寫非原子）。**要用 `threading.Lock` 包住「檢查＋寫入」**，
   第二個 accept 才會確實失敗回「已被 XX 接受」。這是 S1 就該補的併發鎖，不做多人一跑就偶爾掉資料或雙接。

## 8. 待決事項

- **部署模型**：確認走模型 B（建議）還是模型 A+。影響 S1 怎麼寫。
- **登入強度**（S2）：帳號密碼 vs「選名字 + 團隊共用密碼」。看導入時的政治阻力決定。
- **通知管道**（S3）：email 先行 vs LINE bot 先行。
- **手機檢視**（UI #6）優先序：放 S1 還是延到 S3。
- **儀表板的負載可見度**：per-person 負載只給主管，還是也給同儕看？（建議只給主管；速度指標建議不做）
- **自動建立的信心門檻**：高信心自動建 vs 一律進待稽核佇列——初期偏保守到什麼程度。
