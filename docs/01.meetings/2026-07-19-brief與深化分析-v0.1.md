# Part 1|專案 Brief(討論定案)

## 1.1 問題定義

工程圖面的修改要求來源千百種(email、長官口頭、會議記錄、個人筆記),資訊散落且極易遺漏;圖面版本(CAD / Revit / PDF)散落各自電腦,歷史難追;時間壓力下必然漏改圖號與標註,產生正式版、內部版、工地小版交錯的混沌;知識存在人腦,PM 離職即交接斷裂。

本質:這不是專業知識問題,是「人類惰性 + 時間壓力」造成的資料管理問題。痛感極強、無人解決、可視化即價值。

## 1.2 核心概念

圖面界的 GitHub:一個訊息汲取 → 任務派發 → 版本進版的中央管理層。

1. **多源汲取**:以 email 外掛為首選入口 + 一份本地筆記本(口頭轉譯太難,先排除)。
2. **AI 萃取**:辨識訊息屬於哪個專案、哪份圖,轉換成結構化 request,附發件人與直達檔案連結。
3. **任務化執行**:紅燈(待處理)→ 黃燈(pending,已改待確認)→ 綠燈(requester 確認)。點任務開啟該檔的 local copy。
4. **Commit 即進版**:確認時出 PDF、產生流水號、推回中央檔、通知相關人。
5. **完整足跡**:每次進版記錄誰要求、誰修改、誰確認,可追蹤、可交接。

## 1.3 邊界(反覆確認的核心決策)

**只做「文字溝通訊息 → 圖面對應 + 任務派發」這一段,不碰改圖本身。** CAD/Revit 編輯、圖面 diff、自動辨識改動處,屬於邊界以外的另一個系統。

## 1.4 第一階段目標收斂(第二次討論的關鍵收窄)

- **馬上做**:request 對應到「圖的檔案位置」(檔位級)。這是 AI 現在絕對做得到的。
- **先人工**:圖面上的座標級標註——人工手標、系統自動記錄。
- **留到後面**:AI 自動定位座標、自動辨識改動產生 markup/cloud(訓練門檻極高)。

## 1.5 已驗證的脈絡

- Ray 前案:公文丟 AI 自動建 Notion 資料庫,雛形可行但因「仍需人工搬運」+「忙起來無暇顧及」而中斷。反證了全自動汲取的必要性與商業價值。
- ACC 等既有工具在地失敗原因:無法無痕融入既有工作流程。差異化在低摩擦整合與 UI/UX,不在技術。

## 1.6 未來擴充(記錄不做)

法規檢討外掛(接開源建築法規知識庫,commit 時自動 review)、request 附參考資料包(法規條文、技術規定、標準圖連結)、計價單自動化、對接他人知識庫 MCP。

## 1.7 未定案事項

- 協作分工:「各寫各的再 merge」vs「一人先搭 UI 空架」,上次討論未收斂。
- Git pull/push/branch 邏輯搬到圖面檔案的可行性(Ray 待研究)。

# Part 2|深化分析(AI 補充觀點)

## 2.1 好消息:這個東西有名字,而且有整套文獻

你們白板上推導出來的架構,在業界有正式名稱——**CDE(Common Data Environment,共同資料環境)**,定義在 **ISO 19650**(BIM 資訊管理國際標準)。更巧的是:

- ISO 19650 的檔案狀態模型是 **WIP(工作中)→ Shared(共享)→ Published(發布)→ Archive(歸檔)**,和你們的紅燈→黃燈→綠燈幾乎同構。
- 標準裡有完整的命名規則、版次編碼(revision code)、狀態碼(status code)規範,你們的「流水號」問題已有現成答案可抄。

這不是壞消息(「已經有人做了」),而是好消息:**概念已被驗證,詞彙已經存在**。知道「CDE」這個詞,就能打開一整個文獻與產品生態去研究——為什麼現有 CDE 產品(ACC、Trimble Connect)在你們的環境沒被用起來,答案就是你們的產品定位。

同樣地,製造業 20 年前就解決了「二進位檔案版本控制」——叫 **PDM(Product Data Management)**,代表產品是 Autodesk Vault、SOLIDWORKS PDM。它們的 check-out / check-in 模型,就是你們討論的「local copy → 改完 commit 回中央檔」。

## 2.2 Git 類比的一個關鍵修正:Lock 模型,不是 Merge 模型

Git 之所以能讓多人同時改同一份檔,是因為程式碼是**文字,可以逐行合併(merge)**。CAD 是二進位檔,**無法 merge**——兩個人同時改同一份 DWG,必有一人的工作作廢。

所以正確的參照不是 Git 的分支合併,而是 **Lock 模型**(SVN lock、Vault check-out):

> 取出檔案時**上鎖**,其他人只能讀不能寫;改完 check-in 解鎖並進版。

這其實正好解掉你們討論到的「一個人 occupy 檔案一整天,別人打不開」的痛——不是繞過它,而是把它**制度化並可視化**:誰鎖了哪份檔、鎖多久,一目了然。這比現況(檔案被誰開著沒人知道)已是巨大進步。

判準:去研究 Git 之前,先花一小時看懂 Vault 的 check-out/check-in 流程,對這個專案的直接參考價值更高。

## 2.3 雞生蛋問題:Phase 0 其實是「圖面註冊表」

這是我認為討論裡**最被低估的課題**。

「request 自動對應到圖的檔位」有一個隱含前提:**存在一份乾淨的索引**,記載每張圖的圖號、名稱、別名(「91」「管理大樓」)、檔案路徑、目前版次。但現況的痛點恰恰是——這份索引不存在,檔案散落各處。

也就是說,AI 萃取做得再好,沒有對應目標可以指。所以真正的 Phase 0 不是寫 UI,而是:

**建立圖面註冊表(Drawing Register)**:圖號 ↔ 圖名 ↔ 別名 ↔ 檔案路徑 ↔ 版次的對照表。

- 這件事半人工、不性感,但它是整個系統的地基,而且**本身就有獨立價值**(新人找圖問題直接解掉一半)。
- 好消息:可以用 AI 加速——掃描現有資料夾、從檔名與 PDF 內容萃取圖號建立初版,人工校正。
- 判準:一筆 request 能被自動對應的前提,是目標圖在註冊表裡有唯一 ID。註冊表覆蓋率就是系統可用性的上限。

## 2.4 繞道即死:緊急通道的設計

工程界的行為現實:時間壓力下,任何流程都會被繞過。而中央檔的價值建立在「它是唯一真相」——**只要有一次體制外出圖,信任就開始崩解**,大家會回到「還是問人最準」。

對策不是禁止繞道(禁不了),而是設計**緊急通道**:

- 提供一鍵「緊急出圖」:跳過確認流程直接出,但系統仍記錄、事後補登 request。
- 判準:**緊急情況下,走系統要比不走系統快**。做不到這點,系統會在第一個趕圖夜死掉。

同理,官方 PDF 的發布權應該逐步收進系統(只有透過系統 commit 才能產生正式版),這是讓大家不得不用的 forcing function——但要在系統穩定後才收緊,太早收緊會被抵制。

## 2.5 組織與政治課題(技術以外的暗礁)

1. **追責軌跡的阻力**:長官口頭指示被記錄成 request = 留下白紙黑字。有些人**依賴模糊性**(說過的話可以不認帳),他們會消極抵制。導入時需要高層背書,且初期話術應是「保護執行者」(有紀錄 = 改錯不是你的錯)而非「監督指示者」。
2. **email 權限與資安**:外掛要讀公司信箱,圖面是機密。地端部署 vs 雲端、業主資料的授權範圍,商業化前必須面對。自用階段可先擱置,但架構設計時留好地端選項。
3. **AI 對應錯誤的信任成本**:AI 把 request 對應到錯的圖,使用者發現後修正——這個修正動作要被設計成**訓練回饋迴路**(你們已直覺想到 Google 紅綠燈 captcha 的類比,這個直覺是對的,正式名稱是 human-in-the-loop / active learning)。初期準確率不會完美,UI 上「AI 建議 + 人工確認」的設計比「AI 全自動」更能建立信任。

## 2.6 建議的階段重排

| 階段 | 內容 | 判準 |
|------|------|------|
| **Phase 0** | 圖面註冊表(可 AI 輔助建立)+ 專案別名詞彙表 | 現行專案圖面覆蓋率 > 90% |
| **Phase 1** | email/筆記 → request 萃取 → 對應檔位(AI 建議+人工確認)→ 任務清單 UI | Ray 自己一週的 request 全部進系統,零漏接 |
| **Phase 2** | 紅黃綠狀態流 + commit 儀式 + 通知(PDF 先手動上傳) | 一個真實專案跑完整個循環 |
| **Phase 3** | CAD 自動出圖(accoreconsole / Revit API)、座標級標註 | commit 時 PDF 自動產生 |
| **延後** | 自動 diff、法規參考包、計價整合 | — |

## 2.7 動手前的最便宜驗證:兩週人工試跑

在寫任何程式之前,建議先做一個成本近乎零的實驗:**Ray 用一份試算表,人工模擬這個系統兩週**——每一筆收到的修改要求都登錄(來源、專案、圖號、內容、狀態)。

目的不是管理,是**採集真實資料的形狀**:

- request 的真實措辭長什麼樣?(這是之後 prompt 設計的語料)
- 對應圖號時,哪些查得到、哪些查不到?(註冊表的缺口在哪)
- 一週有幾筆?來源比例?(決定 email 外掛值不值得先做)

判準:兩週後這份試算表本身就是 MVP 的規格書 + 測試資料集。這比先寫 UI 空架更能降低「架構蓋在想像的需求上」的風險。

# Part 3|學習錨點(知識地圖)

依「支撐哪個階段」分組。每條給關鍵字,查得到就不展開。

## 3.1 領域概念(支撐整體定位)

- **ISO 19650 / CDE(Common Data Environment)**:你們的系統在業界的正式名稱。重點看:檔案狀態模型(WIP/Shared/Published)、命名與版次編碼規則。
- **PDM / Autodesk Vault**:二進位檔版本控制的成熟解。重點看:check-out/check-in、lock 機制、revision 管理。
- **RFI(Request for Information)流程**:營建業既有的正式請求流程。你們的 request 本質上是「RFI + 內部改圖指令」的數位化,研究 RFI 表單欄位可以直接偷設計。
- **競品研究**:ACC(Issues 模組)、Bluebeam Revu(Studio + 圖面比對)、Revizto。重點不是功能,是**回答「為什麼它們在你們公司沒被用起來」**——答案即定位。

## 3.2 AI / 資料萃取(支撐 Phase 1)

- **LLM 結構化萃取**:function calling / structured output,把 email 轉成 JSON request。現在的模型 few-shot 就能做,不需要訓練模型。
- **Entity resolution / 別名對照**:「91」→「928816 專案管理大樓」這類對應,靠詞彙表 + embedding 相似度即可,不是難題,但詞彙表要人建(見 Phase 0)。
- **Human-in-the-loop 設計**:AI 建議 + 人工確認 + 修正回饋。關鍵字:active learning、confidence threshold。

## 3.3 版本控制思想(支撐 Phase 2)

- **Git 概念層**:commit、版本歷史、單一真相來源的思想值得學;但注意 2.2 的修正——merge 不適用,lock 才適用。
- **SVN lock model / Vault check-in-out**:直接可抄的流程設計。

## 3.4 CAD 自動化(支撐 Phase 3,先淺嚐即可)

- **APS(Autodesk Platform Services,前身 Forge)**:雲端自動化 AutoCAD/Revit 的官方 API,含 Design Automation(無人值守出 PDF)。
- **accoreconsole**:AutoCAD 的無介面批次執行,本地端自動出圖的便宜方案。
- **Revit API / Dynamo**:Revit 端自動化入口。

## 3.5 產品與導入(支撐商業化,最後再深)

- **低摩擦設計**:你們已有正確直覺(遊戲化、無痕融入)。關鍵字:friction audit、Fogg Behavior Model(B=MAP)。
- **工具導入的組織變革**:forcing function 設計、champion user 策略。你們自己就是 pilot customer,dogfooding 是最大優勢。
