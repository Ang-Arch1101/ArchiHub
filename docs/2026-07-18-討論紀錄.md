> 日期：2026-07-18

> 結論：確立產品核心概念「工程圖面的 GitHub」，並定義第一階段邊界與分工。

## 一、痛點（為什麼要做）

1. **圖面版本混亂**：同一張圖存在 PDF、CAD、Revit 多種形式，改動歷史難以追溯，要翻遍各個資料夾才能拼湊出「哪裡改過、誰改的」。
2. **修改要求來源千百種**：Email、會議記錄、長官口頭交代、紙條、個人筆記本……資訊散落，容易漏掉（lose 掉資訊）。
3. **非正式版本氾濫**：工地急著要圖 → 私下先給一版「小圖號」→ 內部又衍生多層非正式版本 → 最後合併時錯誤百出、圖號標註不清。
4. **不是誰的錯，是時間的錯**：時間壓力下漏改圖號、漏改標註是常態；缺的是一套讓錯誤「有順序地被解決」的系統。
5. **交接災難**：需求存在某人腦袋裡、某封信裡；PM 離職後公司花大量時間重新進入狀況。新人連「洗床機在哪張圖」都要問學長。
6. **檔案鎖定問題**：中央檔案被一人開一整天，其他人無法編輯——這正是 Git 早就解決的問題。

> 這些都不是需要尖端知識的問題，純粹是「人類惰性在存東西上產生的巨大問題」。管理在工程界超重要，但大家都以時間為優先，所以沒人做——**商業價值就在這裡**。

## 二、核心概念：工程圖面的 GitHub

軟體工程用 Git/GitHub 管理程式碼；工程界管理的是**圖**。以前做不到，因為軟體沒有「讀圖」的能力——AI 出現之後，這件事第一次變得可能。

### 對應關係

| GitHub 概念 | ArchiHub 對應 |
|---|---|
| Issue / Pull Request | 圖面修改 Request |
| Repository 中央版本庫 | 中央圖面檔案庫（CAD/Revit 源檔 + PDF 出圖） |
| Clone / Pull | 前往任務時自動產生 local copy 進行編輯 |
| Commit / Push | 存檔 + 出圖（PDF）+ 推回中央檔案庫 |
| Review / Merge | 發 Request 的人確認改動符合要求後 Confirm |
| Commit history / 流水號 | 每次進版產生流水號，歷史軌跡清楚可追蹤 |
| Fork（未確認的分支） | 編輯中但尚未 Confirm 的版本，有流水號但不取代中央檔 |

### 三燈狀態流

1. 🔴 **紅燈**：Request 建立，待處理。
2. 🟡 **黃燈（Pending）**：修改完成、已 Submit，等發 Request 的人檢查。
3. 🟢 **綠燈**：Requester Confirm，正式進版、通知所有人。

Confirm 之前，中央 Server 的檔案不會被取代。

## 三、產品定位與邊界（最重要的共識）

**我們只做「溝通資訊 → 圖面」這一段，不碰「改圖」本身。**

- ✅ 邊界內：多來源訊息汲取 → 轉換成結構化 Request → 對應到圖面/檔案 → 派工 → 版本狀態管理 → 進版通知。
- ❌ 邊界外（另一個系統／未來）：自動改圖、圖面 diff 比對（判斷哪些改動值得記錄是大工程）、自動出圖排版、法規檢核、算量估價單。

改圖是另一個架構的事。大家作業方式都不同，連 Autodesk 都沒能力統一整個市場；但共通點是**大家都得出 PDF**——這就是我們的著力點。

### 第一目標（AI 馬上做得到的事）

> **把信件／筆記裡的文字要求，轉換成一個對應到圖面檔案的任務（Request）。**

- 第一階段：Request 對應到「圖的檔案位置」就已經很有價值。
- 進階（可訓練）：對應到圖面上的**具體位置**並自動標註（如「2樓 C7 柱旁的落水頭」→ 自動在圖上標記）。標錯了就人工拖曳修正——這本身就是訓練資料（像 Google 紅綠燈驗證一樣）。
- 每個 Request 附上：對應檔案連結、寄件人/發 Request 人、參考資料（法規條文、標準圖、技術規範）。

## 四、產品型態

- **無痕融入既有工作流程**是關鍵。ACC 之所以沒被廣泛使用，是因為它要求大家改變固有格式與流程；我們要做的是「更無痕的融入」——例如作為信箱插件，AI 讀信自動判斷：這封信屬於哪個專案 → 哪張圖 → 哪個位置。
- **像遊戲一樣低摩擦**：每日任務清單，任務亮燈 → 點下去直接開啟對應的 CAD/Revit 檔案所在位置（不是 PDF，是修改工作的所在處）→ 改完按完成 → 自動出 PDF 進中央檔 → 自動通知。低摩擦、高回饋。
- **模組化 UI**：不同公司格式不同，用可拖拉的小區塊組合（專案名稱、回覆期限、回覆內容……），直覺使用，不需要高技術門檻。
- 介面想像：類似 Notion 的筆記介面 + 旁邊是今日任務表（紅/黃/綠燈），點任務先顯示 CAD 預覽圖 + revision 位置星號標記 → 按「前往」直接跳到修改位置。

### 訊息來源（收斂後）

1. **Email**（首選，最可行）
2. **內建筆記本**：口頭交代自己記下來，AI 辨識筆記對應到哪張圖、自動產生 Request 派給自己
3. ~~語音／口頭即時擷取~~（複雜度太高，先拿掉）

### 領域知識可訓練

專案代號、圖號慣例（如「91」= 管理大樓、「2F C4-7」= 二樓第 C4-7 個柱）只要一開始定義好、教 AI 幾次，它就知道去哪個資料夾找哪份檔。遇到不會的就問——命名不統一的小問題交給 AI 辨識。

## 五、MVP 第一步（分工）

**共識：先把實體做出來，不要空談。**

### A（圖面端）：搭平台空架構
- 一個 UI（master 架構），能讀取兩個本地端資料夾：
  1. 作業檔資料夾（CAD / Revit）
  2. PDF 出圖資料夾
- 能讀入圖面顯示，旁邊列出 Request 清單。
- 先做到這樣就好。目的是先有一個錨點，之後才知道往哪去。

### B（文書端）：定義 Request 格式 + 訊息萃取
- 定義 Request 的欄位：requester、designer、approver、date、改動範圍/位置、回覆期限、參考資料連結、狀態（紅/黃/綠）……
- 先不接 Email API（避開認證/防火牆問題），**先從一堆混亂的 Word/文字檔萃取**出結構化 Request——素材用自己過去的信件內容。
- （B 之前已用 Notion + AI 做過公文整理的雛形，這次目標是全自動化。）

之後兩邊再交織（merge）起來。

## 六、未來擴充（記下但不現在做）

- Request 自動附帶對應法規、技術規範、標準圖連結（畫圖前不用自己 study）
- 法規檢核：Push Request 時檢查與建築法規的衝突（接開源法規知識庫 MCP，如社群已有人維護的建築法規知識庫——開源共維，價值在 UI/整合層）
- 圖面 review agent：讀 PDF 檢查明顯錯誤、自動產生系統 Request
- 算量、估價單串接、自動發送
- 業主端視圖：從歷史中篩選與自己相關的事項 → 所屬圖面 → 任務列表，方便管理與交接
- 每張圖進版都記錄 approver / designer，責任歸屬清楚
